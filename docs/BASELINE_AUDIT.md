# M0 baseline audit

## Scope and evidence status

This audit captures the legacy consumer safety defects before changing production code. M0 does **not** fix these defects or establish trading readiness. The inspected legacy checkout is baseline `e7dceaf9492e4b5413ea3a972b66db7474b0232f`, as identified by the integration owner. The upgrade brief is `LIMIT_ORDERBOOK_OMP_UPGRADE_PROMPT.md`, sections 2, 5, 10, and 11.

The integration owner reported **35 existing offline tests passing** in the repository `.venv` on Python 3.9, with a LibreSSL warning. That is supplied baseline evidence, not a test run performed by this audit worker. No live validation, browser session, benchmark, soak, test, formatter, lint, or build was executed by this worker. The new regression suite's results must be recorded by the integration owner after running it; they are not claimed here.

All behavior predictions below are **[INFERENCE] from inspected source**, with executable synthetic reproductions in `tests/test_upgrade_regressions.py`. Source line references refer to the unchanged legacy files. No `AGENTS.md` was found in the searched repository or ancestor locations.

## Regression harness and interpretation

Every new regression uses `xfail(strict=True, raises=AssertionError)` with a defect-specific reason. The test body expresses the desired safety outcome, not an assertion that the bug remains. A fixed behavior therefore produces a strict XPASS failure until its marker is removed. Import failures, missing attributes, unexpected parser exceptions, and other non-assertion errors are not swallowed as known defects. Expected validation errors are handled specifically as `ValueError`; accepting the invalid input raises the explicit assertion used by xfail.

The tests call the current production APIs, including `make_snapshot`, `LiveBook.apply`, `KrakenAdapter.handle_ws_message`, `components.render_comparison`, `FeedWorker._run_ws_once`, the real reconnect/REST loops, and `OrderBookService.set_subscription`/`stop`. Fakes replace external WebSocket transport, Streamlit output sinks, thread startup, REST responses, and elapsed waits only. No fixture contacts an exchange, submits an order, needs credentials, sleeps, or starts a real worker thread. All exchange payloads are synthetic, not claimed to be captured live data.

Important limits:

- Comparison assertions exercise the actual emitted metrics, not screenshots or browser interactions. The mixed-quote regression captures the concrete fictitious-cross symptom; M1 still needs positive tests for separate cohorts, explicit exclusion reasons, conversion orientation, and legitimate same-quote cross-venue opportunities.
- The stale fixture covers a plainly old observation, not configurable small as-of skew, exchange clock offset, or differing receive/event timestamps. Those contracts do not exist in the current model.
- The Kraken depth fixtures follow the existing tests' minimal book schema and do not include checksums. They isolate the current depth bug. When checksum validation is added, migrate these fixtures to fully valid checksummed messages while preserving the depth invariant; do not weaken validation to keep minimal fixtures working.
- The ownership fixture models two consumers of the actual same service object because that is how the entrypoint is wired. It is not evidence that two real tabs were exercised. When a per-client registry is implemented, migrate this regression to two actual subscription handles, with shared physical-feed reference counts and independent unsubscription.
- The shutdown tests observe cancellation/join requests through inert workers. They do not measure real thread completion or prove that blocking network calls terminate promptly. M1 needs integration cancellation and stale-epoch tests in addition to these deterministic reproductions.
- Recovery time is virtual and bounded. This demonstrates the missing recovery transition without claiming a live reconnection measurement.

## Additional audited risks and missing capabilities

These are source findings, not additional claimed regression runs:

- **Precision, identity, and time:** `src/domain/models.py:9-10,42-51` uses float pairs, venue/symbol strings, and one ambiguous timestamp. `make_snapshot` substitutes local wall time at `:128`; no distinct receive monotonic/event/publish times or connection epoch exists in this contract. Exact decimal text and full instrument metadata must be introduced before claims of executable comparison correctness.
- **Kraken protocol validation:** `src/data/adapters/kraken.py:55-68` does not inspect checksum or incoming symbol, and has no initialized/synchronized gate. A nonempty two-sided update can be treated as a book without a prior snapshot. The depth regression is not a complete Kraken conformance test.
- **Bybit continuity/reset semantics:** `src/data/adapters/bybit.py:56-69` accepts any `orderbook.` topic, applies data, and forwards `u` as metadata without continuity/reset validation. Do not write a fabricated contiguous-ID rule; use the documented protocol and fixtures for that API family.
- **Coinbase API-family confusion:** `src/data/adapters/coinbase.py:1-4,14-21` asserts that level2 WebSockets require authentication, disables streaming, and uses Coinbase **Exchange** REST. That local statement does not establish the requirements of **Advanced Trade** public level2. Connector research must verify its endpoint/schema independently; this audit did not run a Coinbase network probe.
- **Heatmap coordinate instability:** `src/ui/components.py:234-259` recomputes percentiles and bin edges from the entire visible history on every render. Adding observations can change where previous liquidity is binned. `src/domain/orderbook_service.py:183-185,255-261` stores only bounded in-memory sampled snapshots. This is not durable recording or an event-complete heatmap.
- **Acceptance beyond M0:** no claim is made here of a trade tape, durable recording/replay, cost-aware execution estimator, paper ledger, predictive signal validity, reference-counted subscription registry, or new backend/frontend implementation. These require their own milestone implementation and evidence.
