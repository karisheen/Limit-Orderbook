# Flat upgrade backlog and acceptance criteria

Scope source: `LIMIT_ORDERBOOK_OMP_UPGRADE_PROMPT.md`, sections 1–14. This file preserves **all required M0–M6 acceptance work**, not only headline features. M0 documentation does not implement later milestones. Every row is independently reviewable and must cite actual evidence before closure. Dependencies follow M0 → M1 → M2 → M3 → M4 → M5 → M6; tests/instrumentation accompany the feature rather than being postponed until M6. Optional features are explicitly distinguished from requirements. `[ ]` means not certified complete here; the integration owner records executed checks/results and any changed decisions in `OMP_UPGRADE_HANDOFF.md` and updates completion status.

## Closure rules

A row closes only on its actual acceptance evidence, not a plausible implementation or upstream capability claim. Mark blocked capability explicitly and finish independent reachable work; successful raw HTTP/WS access does not prove synchronization, checksum integrity or complete capture. Measurements identify fixture/hash/runtime and distinguish synthetic loads, recorded real traffic and live feeds. Small source-inspection spikes do not imply installed-library parity. All relevant tests/callers/docs migrate with a changed contract. Optional themes/derivative venues/passive simulation/calibrated micro-price do not displace required Hyperliquid or core terminal workflows.

M0 execution results and next concrete implementation action belong to the handoff. This backlog is intentionally flat so requirements cannot disappear inside broad milestone headings.
