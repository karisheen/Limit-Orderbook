# Public USD spot adapters

These adapters implement `src.workstation.adapters.base.Adapter` using the exact workstation contracts. They perform no authenticated calls or execution. Offline fixtures live in `tests/test_workstation_usd.py`; their existence is not a claim that integration checks or live adapter validation have run. The parent integration owner records executed verification separately.

## Identity, discovery, and timestamps

- `KrakenAdapter`: venue `kraken`, API family `spot-v2`, stable ID `kraken:spot-v2:spot:BTC/USD` (and metadata-discovered equivalents). Public REST `AssetPairs` supplies native pair/asset identifiers, tick size, lot precision, minima, and status. Only products with a public WebSocket symbol are admitted. Documented `XBT → BTC` and `XDG → DOGE` aliases select v2 symbols; internal identifiers remain in `native_asset_id`/`native_token_id`.
- `CoinbaseAdapter`: venue `coinbase`, API family `advanced-trade`, stable ID `coinbase:advanced-trade:spot:BTC-USD`. Discovery uses only `/api/v3/brokerage/market/products?product_type=SPOT`, follows bounded cursor/offset pagination, and retains exact `price_increment` (not `quote_increment`), `base_increment`, minima/maxima, and product status. Duplicate products/pagination loops fail instead of yielding an incomplete catalog. Products whose `alias` identifies another unified book stay visible as `unavailable`/`unsupported`; they cannot subscribe as separate USD/USDC liquidity. No Exchange products or book schemas are substituted.
- Shared canonical29 crypto IDs cover **BTC, ETH, SOL, XRP, DOGE, ADA, LTC, LINK, AVAX, DOT, BNB, TRX, HYPE, SUI, BCH, UNI, NEAR, APT, AAVE, ETC, ENA, ATOM, ARB, OP, INJ, FIL, SEI, TIA, WIF**. The last 19 extend the original ten under the explicit curated policy in `instruments.py`; this is not general ticker equality or a promise that each venue lists every pair. Unknown, wrapped and network-prefixed assets stay distinct/venue-scoped. USD, USDT and USDC also have common IDs but are never equated with each other.
- Metadata versions combine the content digest with fetch nanoseconds: identical bytes fetched later cannot collide with an immutable version that includes a different `metadata_asof_wall_ns`. Newly parsed descriptors involving one of the 19 added base, quote or settlement identities also receive `:canonical-assets-v2`. The suffix versions the changed mapping, not the payload: source bytes/hash and fetch provenance remain intact. It is not a wire migration; old captures retain their original IDs and descriptor versions, including older venue-scoped identities. Kraken's snapshot hash covers raw response bytes; Coinbase's multi-page hash covers the ordered concatenation of each exact response prefixed by its eight-byte big-endian length. Discovery leaves data/execution access unknown; successful metadata access is not a book/trade/execution capability probe.
- Both decoders use `exact_json_loads`; numeric JSON tokens become exact Decimal values before any checksum or validation. `parse_rfc3339_ns` accepts up to nine fractional digits and explicit RFC3339 offsets, with integer nanosecond arithmetic. Missing exchange times remain absent. Coinbase envelope time is labeled `message`, individual level times remain on changes, and trade time is labeled `trade`. Receive timestamps and ordinal are attached separately by `wrap_decoded`.

Discovery acquires official public metadata through shared `transport.fetch_public`, not a substitute exchange's schema or an unofficial proxy. Complete authoritative family results alone can retire missing products in the catalog; failed/incomplete acquisition does not justify retirement. Missing-product descriptors become `unavailable` with that family's source, hash and fetch-time provenance, while existing streams/captures retain their pinned versions. Coinbase's pagination must finish before its result is published. For independent Binance/Bybit family discovery and the strictly transport/5xx-only official Bybit metadata peer policy, see [Asian adapters](ADAPTERS_ASIAN.md#metadata-and-identity); that peer policy is not a general host fallback for these USD adapters.

Shared HTTP pacing honors `Retry-After` seconds or HTTP dates for retryable 429/5xx responses through an origin-wide request-start deadline. Waiters recheck extensions, and delays above 120 seconds open the circuit instead of retrying early. HTTP 403/451 remains an access denial, never permission to bypass it through another host. These rules do not certify current network access.

Catalog candidates, verified session-pinned financial metadata, observed usable books and observed trades are separate readiness evidence. Neither a catalog entry nor a subscription acknowledgment proves received market data, and book readiness does not prove trade readiness. Discovery selectors may expose newer descriptors, but costs/paper financial interpretation uses the selected session's exact pinned metadata, not a silent upgrade. Native venue, symbol, quote and settlement identity remain authoritative; aggregate display grouping does not supply FX evidence or execution permission.

## Kraken WebSocket v2 and REST snapshots

Endpoint: `wss://ws.kraken.com/v2`. Book keys require an explicit reconstruction depth from 10, 25, 100, 500, or 1000; the workstation default is **25**. A book owner subscribes only to the book snapshot/update channel; a separate trade owner subscribes only to public trade history/live prints. Kraken supplies automatic connection heartbeats; no client application heartbeat subscription is required.

The reducer consumes a whole decoded source message atomically. Absolute replacements, zero deletions, and repeated same-price changes retain source order. Transient intermediate crosses are not published or validated before the entire message has been applied. The retained book is truncated to the actual subscribed depth after each message, since levels falling outside that depth need not receive deletions. A 25-level book plus a better insertion therefore remains 25 levels. UI display depth must not alter this key.

Every WebSocket book snapshot/update requires an unsigned CRC32. After applying the message and truncating, CRC input is the top ten asks ascending followed by the top ten bids descending, concatenating price and quantity with decimal points and leading zeros removed. Trailing lexical zeros are preserved, including when an update replaces a numerically equal price having a different lexical scale. A mismatch, missing checksum, wrong symbol, invalid schema, or invalid candidate requires recovery; heartbeats do not repair invalid state. No usable WS book exists before a validated native snapshot. Wrong-symbol/schema decode errors are surfaced to supervision without partial events; supervision owns invalidation/reconnect.

Kraken book keys advertise snapshot/delta flow and a top-ten checksum scope; trade keys advertise trade flow. Neither invents a sequence guarantee, and bounded book coverage is not full depth. WebSocket initialization and checksum recovery always use a native v2 snapshot. REST is never used to seed WS CRC state.

Book `snapshot_request` uses the public `/0/public/Depth?pair=<instrument.native_asset_id>&count=<key.depth>` endpoint. The decoder requires the exact REST endpoint, native result key and successful error envelope; levels retain their original decimal strings. Per-level timestamps do not become an invented whole-book exchange timestamp. The result is an independent `BookUpdate("snapshot", ..., subscribed_depth=key.depth)` without WS checksum or sequence evidence. Supervisor fallback and probe preflight use shared `make_snapshot_reducer`: bounded, independently validated, degraded REST observations with no continuous-event/checksum claims. Returning to WS starts a new synchronization segment. Public REST trades are not exposed.

Trade `side` is explicitly the **taker** side. Keys are immutable `instrument_id:trade:trade_id`, since Kraken trade IDs are unique per book, not across all products. Snapshot prints are labeled subscription history; raw duplicates remain decodable for deterministic replay and downstream deduplication.

## Coinbase Advanced Trade

Endpoint: `wss://advanced-trade-ws.coinbase.com`. No JWT is sent. A book owner subscribes to `level2` and `heartbeats`; a separate trade owner subscribes to `market_trades` and `heartbeats`. Each decoder rejects the other data channel. Incoming `l2_data` (and `level2`) uses `new_quantity` as an absolute quantity. Reconstruction keys have `depth=None` and no source aggregation. The full WS snapshot is retained: there is no 25/200-level display truncation. The reducer has an explicit safety capacity of **100,000 levels per side**; overflow invalidates/resynchronizes instead of silently trimming. The shared raw-message bound is 32 MiB. An offline synthetic fixture exceeds 4 MiB and reconstructs 40,405 bid levels, matching the scale of the previously observed large snapshot without claiming that observation verifies this adapter.

`sequence_num` is **connection-global across every frame**, not per book/product/channel. Ordered decoded ack/heartbeat events carry the same sequence provenance as data events. The first connection message must be sequence zero; subsequent accepted messages must increment by one. All events within one frame share that sequence and are consumed once atomically. Equal/older sequence frames are ignored as duplicates; a forward gap invalidates the state, including if the frame purports to be a new snapshot. A snapshot cannot mask missing connection frames. Offline flows cover independent book/trade connections, including acknowledgments, heartbeats, empty trade batches and gaps on each. The subscription acknowledgment identity for connection-scoped heartbeats is `"heartbeats"`; data-channel identities must match the exact instrument product symbol. Dedicated physical ownership per subscription is required; multiplexing or filtering frames ahead of this decoder would invalidate that contract.

The public Advanced REST fallback is `/api/v3/brokerage/market/product_book?product_id=...&limit=1000`, decoding `pricebook` with object levels `{price,size}`. It is a bounded independent snapshot, **not** a sequence bridge for WS bootstrap. Supervision must use its separate REST snapshot/degraded reducer, strip continuity/checksum/exact-flow capabilities, and segment transitions back to WS. WS initialization waits for the native level2 snapshot. `api.exchange.coinbase.com` and Exchange array-level schema are never used. Endpoint access restrictions remain explicit failures rather than authentication/schema fallback claims.

The Advanced `market_trades.side` field is the **maker's** side. `BUY` normalizes to taker `sell`; `SELL` to taker `buy`; missing/unrecognized side remains unknown. Trade IDs are kept as strings, including values larger than JavaScript's safe integer range. Immutable dedup keys include the complete instrument ID plus trade ID and do not incorporate receive time, connection epoch, or history status. The initial trade snapshot is explicitly history, not a claim of complete past execution coverage.

Both trade decoders validate positive exact price and quantity against the instrument's price tick and quantity lot before emitting any trade. No rounding or float conversion repairs an off-increment print; one invalid trade rejects the entire source batch, including preceding valid prints, with the raw frame hash. Valid decimals retain their original lexical scale. These checks do not change maker/taker interpretation, history flags, immutable dedup IDs or Coinbase connection sequencing.

## Offline acceptance coverage and limits

Fixtures cover whole-message application, the published Kraken CRC vector, numeric lexical precision, depth eviction, repeated changes, missing/mismatched CRC, malformed/negative/nonfinite/excess-precision inputs, wrong symbols, empty/crossed/duplicate snapshots, invalid ticks, no-snapshot gating, Coinbase independent book/trade connection sequencing, duplicate/gap/epoch rejection, full-depth bounds, native REST separation, Kraken REST native-key/endpoint/schema validation and degraded snapshot reduction, side normalization/history/dedup, subscription rejection, capabilities, metadata discovery/pagination/status, and timestamp nanoseconds. Run through the parent integration test command; this implementation task deliberately does not execute tests, formatters, type checks, or network probes.

This document does not certify live access, live synchronization, account trading eligibility, loss-free historical trade coverage, or profitability. A checksum protects Kraken's WS top ten levels, not independently every deeper price; Kraken REST snapshots carry no such checksum evidence. Coinbase's REST fallback does not represent its complete WS depth. Current public data and metadata never supply missing historical books.
